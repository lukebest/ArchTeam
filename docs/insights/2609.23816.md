## 四视角独立批评

### 微架构

生产级 LLM decode 要低时延、高带宽、大容量，当代单一介质三者难兼。HBM 给注意力 decode 带宽但容量有限；片外 DRAM/CXL/SSD 给容量但带宽约低两个数量级。HBF 把 NAND 经 TSV 堆在 GPU 旁，容量密度远高于 DRAM，聚合读带宽可接近 HBM，但访问是 KiB 级页、µs 级 t_R，靠数千 plane 并行凑带宽，且写耐久有限。前三页结构主张：HBM+HBF 作层次，对 GPU 呈现单一逻辑 KV 内存；自定义 HBM/HBF base die 把放置、搬移、检索、回收藏在内存接口之下；新条目进 HBM，更老页一次性迁到 HBF，选中页经同一接口回读。稀疏注意力若仍按 HBM 细粒度假设设计，会对不上页粒度与 plane 占用。Modeled stack：16 die × 64 plane = 1024 plane，4 KiB page，256 pages/erase block。反向工程：base-die 控制面、页映射表位置、plane 调度与 t_R 重叠——均在未读节。

### 负载

Decode 每步读权重与累积 KV，算术强度低、带宽受限；上下文与并发共同放大 KV 足迹。具象压力：Qwen3-235B-A22B 上 64 路并发、每路百万 token 的 KV 约 12.9 TB，相当于约 68 块 B200 的 HBM 容量（尚未计权重）。即便 GQA/latent，单 token 仍可向 cache 追加约 128 KiB；约 192 GB HBM3E 需同时装权重与并发请求。服务目标常用 TPOT（如 100 ms/token）约束下的可持续吞吐。稀疏注意力动机：长历史注意力质量集中在 sink、近邻与少量 query 相关子集——但既有稀疏法按 HBM/DRAM 细粒度与可重排假设设计，与 flash 页读/不可原地改写冲突。

### 仿真方法学

Abstract 在 100 ms TPOT 目标下声称每 GPU decode 吞吐 3.5×–11.4×、精度相对稠密注意力差距 ≤4%——unpaid。前三页给出的表征数字（12.9 TB / 68 GPU / 5× HBF / 16K→1M 吞吐跌幅 / 17 vs 5 GPU）来自 Fig.1 动机曲线，非完整实验设定。贡献列表点名 OpenHBF（事件驱动 serving + 实测 GPU kernel + 互连/base die/plane 模型），细节 unread。勿把 Fig.1 示意倍数当作已付清评估。

### 工业可行性

产品命题是包装级 HBF 与自定义 base die，而非再堆 GPU 只为扩 KV 容量。工业墙：HBF 写耐久与 erase、页粒度与稀疏选择的匹配、base-die 逻辑是否进入可流片的定制 HBM/HBF 路线、以及“虚拟成单一内存”对 GPU 驱动/运行时的兼容。PCIe/CXL 二级存储已证明带宽鸿沟难靠预取/分块抹平；HBF 若读带宽/字节与能耗仍差于 HBM，则必须保证只读小比例历史且极少覆写。前三页未给成本、功耗或控制器面积。

## Master Class

1. **The Real Abstract** — Long-context decode needs TB-scale KV and near-HBM read bandwidth; HBM lacks capacity, CXL/SSD lack bandwidth. HBF offers both density and aggregate bandwidth but only at page/plane granularity with weak write endurance — so KV virtualization across HBM+HBF and sparse retrieval must match those physics.

2. **The Rashomon Synthesis** — Serving systems page KV and spill to host/SSD; sparse-attention people pick tokens for HBM; packaging people put flash beside the GPU. Leftover: a hierarchy whose secondary tier is *not* bandwidth-starved, but whose access quantum and write rules break HBM-era sparse designs.

3. **The Magic Trick** — Present HBM+HBF as one logical KV memory behind custom base dies; co-design sparse page retrieval with plane-parallel flash reads and write-once placement.

4. **The Skeleton in the Closet** — Abstract 3.5×–11.4× unpaid; Fig.1 GPU counts are motivational; write-endurance budget and base-die complexity unread; accuracy “within 4%” unpaid.

5. **可提取的问题线索**（仅 p.1–3，有数字，无机制名）

1. Qwen3-235B-A22B 上 64 路并发、每路约 100 万 token 的请求，其 KV cache 合计约 **12.9 TB**，足以填满约 **68** 块 B200 的 HBM（尚未计入模型权重）。(p.1)
2. 仅为扩容量而增加 GPU，会在 decode 阶段进一步过度配置本已低利用的算力；跨 GPU 池化 KV 又引入复制或通信开销。(p.1)
3. 主机 DRAM / CXL / SSD 等二级介质可扩大 KV 容量，但 PCIe/CXL 带宽大约比 HBM **低两个数量级**；预取、分块、缓冲无法抹平这一带宽鸿沟。(p.1)
4. HBM 以数百字节、纳秒级时延访问；flash 以约 KiB 级页、微秒级时延访问。要接近 HBM 聚合带宽，需在堆栈内对 **数千** 可独立访问的 plane 做大规模并行。(p.2)
5. 上述 12.9 TB 的 KV，若改用 HBF 容量，约 **5** 个 GPU 的 HBF 即可装下（对比约 68 个 GPU 的 HBM）。(p.2, Fig.1)
6. 在 Fig.1 示意下，对 HBF 做全历史稠密注意力时，每 GPU 吞吐从约 16K 上下文到 1M token 可跌超一个数量级，并在 1M 时需要约 **17** 个 GPU；若只读 query 相关的历史子集，吞吐损失可压到约 **2×** 以内，1M 时约 **5** 个 GPU 且相对纯 HBM 方案每 GPU 吞吐可高约一个数量级。(p.2, Fig.1)
7. 即便采用分组 KV，单 token 仍可向 cache 追加约 **128 KiB**；约 **192 GB** 的 HBM3E 需同时容纳模型权重与并发请求的 KV，长上下文可在算力耗尽前先耗尽容量。(p.3)
8. 所建模 HBF 堆栈含 **16** 个 die、每 die **64** 个 plane，共 **1024** 个 plane；页大小 **4 KiB**，每个 erase block **256** 页。可用带宽只有在读请求能跨这 1024 个 plane 并行时才接近 HBM。(p.3, Fig.2)
