# 2609.02352: Atlas — On-Device City-Scale 3DGS in VR (first-3-pages note)

- arXiv: [2609.02352](https://arxiv.org/abs/2609.02352) · PDF: [arxiv.org/pdf/2609.02352](https://arxiv.org/pdf/2609.02352)
- Venue: ACM-style preprint (v1 2 Sep 2026; cs.AR). Extension of ASPLOS'26 Nebula (cloud-collaborative); this version claims fully on-device.
- Domain tag: mobile GPU memory hierarchy / neural rendering
- One-line hardware fact (from p.1–3 only): on-device city-scale 3DGS path that keeps only the active Gaussian working set in device memory (block-wise hierarchical offload + async load), plus temporal-aware LoD traversal and stereo-view reuse with a lightweight line buffer for dual-eye rasterization.
- Reading scope: **PDF pages 1–3 only** (title through start of §2 LoD tree). Methods/eval unread by design.

## 四视角独立批评

### 微架构

The intro already names the boxes. Mechanism candidates visible by p.3: (1) spatial block partition with on-demand load from lower-tier storage into GPU memory; (2) async working-set tracker overlapping DMA with render; (3) temporal-aware LoD tree walk that streams DRAM and skips redundant nodes across frames; (4) stereo pipeline that shares preprocess/sort between eyes; (5) a **line buffer** holding left-eye Gaussians for right-eye reuse (p.3). That last one is the only concrete microarchitectural widget named in the first three pages — capacity, ports, and eviction are not given. Everything else is a software/runtime story until §8 (unread). Reverse-engineer question: is the line buffer a few scanlines of splat metadata or a general reuse cache? Intro does not say.

### 负载

Stress claim is city-scale 3DGS for mobile VR: memory up to **66 GB** vs typical mobile VR **<12 GB** (p.2), plus LoD hierarchy that stores extra tree state. Navigation implies spatio-temporal correlation of visible Gaussians (Fig. 5–6 cited, not shown in text extract). Workload reviewer wants: which city scenes, walk vs fly camera, target motion-to-photon budget, whether LoD quality is measured. None of that is numeric on p.1–3 beyond the 66 GB / <12 GB gap. Stereo doubles the view count by construction.

### 仿真方法学

First three pages assert **18.5×** motion-to-photon vs mobile GPU, **3.9×** vs SOTA 3DGS accelerators, **92.4%** energy cut, up to **7.0×** on-device memory reduction, LoD search up to **8.1×**, rasterization **1.9×** (p.1–3). No simulator, node, or baseline named yet. Treat these as author claims pending §10 (unread). Extension note vs Nebula (ASPLOS'26) is useful: prior work used cloud; this claims offline on-device (p.1 footnote).

### 工业可行性

Product constraint is honest: no runtime Internet (p.2). That forces a full scene on disk/SSD and a working-set manager that must not hitch. Disk→GPU bandwidth and thermal limits on a <12 GB VR SoC are the industrial wall; intro does not budget them. "Negligible hardware overhead" for the line-buffer augmentation (p.3) is an unpaid check until area/energy of that buffer appear.

## Master Class

1. **The Real Abstract** — City-scale 3DGS needs tens of GB; phones have <12 GB. Keep only pose+LoD-active Gaussians in GPU memory via hierarchical block offload and async loads; speed LoD walk with temporal coherence; share stereo work; add a small line buffer so right-eye rasterization reuses left-eye Gaussians. Claimed 18.5× / 92.4% energy vs mobile GPU (p.1–3).

2. **The Rashomon Synthesis** — Microarch cares about the line buffer and whether offload is HW or driver; workload cares whether 66 GB scenes and VR navigation are representative; tools refuse the speedup table until methodology appears; industry asks about SSD bandwidth and hitch-free MTP. Agreement: the memory gap is real. Disagreement: whether the intro's framework is a new chip or a systems paper with a small HW nudge.

3. **The Magic Trick** — The full model is huge, but each frame only needs a small visible+LoD subset — so treat GPU memory like a cache over disk-resident Gaussians.

4. **The Skeleton in the Closet** — Extends Nebula (cloud) to on-device (p.1); first three pages do not quantify disk BW, hitch rate, or line-buffer size; big speedups are front-loaded before method sections.

5. **可提取的问题线索**（仅 p.1–3，有数字，无机制名）

1. 城市场景级神经点绘表示的常驻体量可达约 **66 GB**，而典型移动 VR 设备 GPU 内存 **<12 GB**，二者差一个数量级以上。(p.2)
2. 为远近细节切换引入的层次细节表示会额外占用内存（树/层次节点与相关元数据），在已超容量的场景上进一步加剧驻留压力。(p.2)
3. 依赖网络把大体量模型或中间结果卸到远端的路径，在移动 VR 无法保证连通时不可用；目标场景要求渲染期离线。(p.2)
4. 流水线前段（可见性 / 细节等级选择）需要触达的图元集合远大于后段实际着色集合，内存峰值出现在前段。(p.2)
5. VR 需同时产出左右眼两路紧耦合视图，若不共享中间结果，预处理与排序等阶段会对第二只眼重复付费。(p.2–3)
