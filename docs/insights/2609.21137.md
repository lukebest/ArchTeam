## 四视角独立批评

### 微架构

Scratchpad-based tensor accelerator (STA): software-managed SPM + DMA between HBM and SPM; multiple heterogeneous engines (tensor, vector, scalar/SIMD). Exemplars named: Trainium, TPU, Gaudi 2, Ascend. Problem framing on these pages: MoE decode latency on STA is dominated by expert-weight DMA while engines idle; experts known only after routing, so prefetch windows are short; staging pre-route experts in limited SPM conflicts with compiler locality / reclaim. Representation axis: shrinking traffic (sparse formats, VQ, low-rank) can raise packet count / irregularity so DMA service time does not fall with byte count; VQ alone needs per-expert index→codebook lookup. Engine axis: routing → weight transfer → expert compute is a strict dependency chain; finer-grained up/down projection split across engines adds operand deps and SPM traffic. Proposed structure (name for indexing only): hybrid expert-weight = shared low-rank basis per layer in SPM + small private coefficients, plus shared VQ codebook; dataflow breaks into expert-common vs expert-private parallel phases with mixed compute/IO tasks. Platform sketch (p.3): Trainium3 — 8× NeuronCore-v4, 144 GiB HBM @ 4.7 TB/s; per core 32 MiB SBUF, 2 MiB PSUM, 16 DMA engines; tensor engine 128×128 stationary matmul; vector/scalar elementwise; GpSimd programmable SIMD; programmed via NKI. Fig. 1 / Table 1 / Fig. 2–3 are on these pages; full CARDAN schedule unread.

### 负载

Autoregressive MoE decode (not prefill): prefill is many-token compute-bound; decode is one-token-at-a-time memory-bound and can exceed half of end-to-end latency for long outputs. MoE block: router picks k of E experts, each applies gate/up/activation/down; acting expert set can change every token → little weight reuse from HBM. Concrete load on p.1: Qwen3-30B-A3B — 48 layers, 8-of-128 experts active, ~75 MB BF16 weight traffic per layer per token under 4-way tensor parallel on Trainium3 (4 logical NeuronCores × 64 MiB SPM). Same figure also shows Gemma 4 (30 layers) and Nemotron 3 (52 layers). Attention is de-emphasized: on Qwen3-30B-A3B attention is only 3.03% of weights and 10.4% of end-to-end decode latency (p.3). Named families for unread eval: Qwen3, DeepSeek-V2-Lite, Nemotron, OLMoE, Gemma4.

### 仿真方法学

Abstract speedups (1.15–1.31× batch-1 over AWS dense MoE megakernels; 1.7× at batch 16; BF16-teacher perplexity matched/improved) are unpaid until unread eval. Paid characterization on p.1–3: Fig. 1 latency breakdown percentages; LR-only perplexity 9.82→34.91; VQ runtime up to 20% e2e; SIMD/vector active-time fractions; Trainium3 resource numbers. No cycle-accurate simulator named on these pages; measurement appears to be real Trainium3 / NKI. Treat all abstract end-to-end speedups as unpaid.

### 工业可行性

Product move is MoE decode on shipping STA (Trainium-class) via weight representation + multi-engine schedule, not a new ASIC. Adoption constraints already on these pages: SPM capacity vs prefetched expert buffers; compiler reclaim can invalidate prefetch; DMA service depends on packets/address regularity not only bytes; quality cliff of pure low-rank (ppl 9.82→34.91); VQ lookup tax up to 20% if used alone. Claims are Trainium3-specific; portability to TPU/Gaudi/Ascend SPM+DMA stacks is asserted by analogy only on p.1–3. Abstract 1.15–1.31× unpaid.

## Master Class

1. **The Real Abstract** — On scratchpad tensor accelerators, MoE decode is expert-weight DMA with idle engines: routing late-binds which weights to fetch, SPM is too small to stage guesses, and shrinking the matrix can make DMA worse. Need a representation that keeps a shared on-SPM basis/codebook and a dataflow that overlaps DMA with the idle engines.

2. **The Rashomon Synthesis** — MoE-systems people prefetch from history or compress experts; STA compiler people maximize SPM locality and reclaim; quantization people VQ the weights. The leftover problem is late-bound expert traffic on an explicitly managed multi-engine scratchpad where prefetch, reclaim, and lookup tax fight each other.

3. **The Magic Trick** — Hybrid VQ + shared low-rank expert weights; split expert-common vs expert-private phases so DMA overlaps concurrent tensor/vector/SIMD engines.

4. **The Skeleton in the Closet** — Abstract 1.15–1.31× / 1.7× unpaid; LR-only quality cliff is huge (9.82→34.91); VQ alone costs up to 20% e2e; Trainium3 SPM/DMA specifics may not transfer; full schedule unread past p.3.

5. **可提取的问题线索**（仅 p.1–3，有数字，无机制名）

1. Qwen3-30B-A3B 共 48 层，每层每 token 仅激活 128 个专家中的 8 个，却仍产生约 75 MB（BF16）的专家权重流量/层/token；作用专家集可随 token 变化，HBM→片上暂存几乎无复用。(p.1)
2. 在四路张量并行的示例 STA（每逻辑核约 64 MiB 软件暂存）上，Qwen3 专家权重装载占端到端解码延迟约 56%，其中约 36.8% 暴露在关键路径上。(p.1, Fig.1)
3. 同设置下 Gemma 4（30 层）关键路径暴露的装载约占端到端 42.5%；Nemotron 3（52 层）约占 30.5%。(p.1, Fig.1)
4. 仅用低秩近似重建专家权重时，Qwen3-30B-A3B 困惑度从约 9.82 升至约 34.91，质量损失严重。(p.2)
5. 向量量化虽能缩小权重流量，但按码本取码字的运行时开销在 Trainium 评测中可占端到端解码延迟最高约 20%。(p.2)
6. 同 Qwen3 轨迹上，SIMD 引擎活跃时间仅约 4.1%–4.7%，向量引擎仅约 7%–10.1%，计算引擎大量闲置。(p.2)
7. 现代 MoE 中注意力相对专家计算更轻：Qwen3-30B-A3B 上注意力约占整体权重 3.03%、端到端解码延迟约 10.4%。(p.3)
8. 示例平台单设备含 8 个 NeuronCore-v4、约 144 GiB HBM（约 4.7 TB/s）；每核约 32 MiB 软件暂存、约 2 MiB 累加器、16 个 DMA；张量引擎为 128×128 收缩阵列——专家权重仍需经 DMA 从 HBM 灌入有限暂存。(p.3)
