## 四视角独立批评

### 微架构

Target: FPGA-based SmartNIC receive datapath for RDMA over multi-path lossy WAN (scale-across AI factories). Problem structure on these pages: conventional NIC tracking uses sliding-window bitmaps sized to cover all in-flight packets → state linear in BDP (= bandwidth × RTT); WAN RTT and Tbps-class links blow past FPGA BRAM; multi-path packet spraying adds reordering/jitter that single-path WAN or intra-DC bitmaps do not size for. Prior FPGA trackers (IRN, OmniDMA, shared-bitmap pools, LoWAR) either size to intra-DC BDP, omit multi-path/jitter, keep state ∝ in-flight packets, or track only one coding block. SoC/software partial offloads (SDR-RDMA on BlueField-3, host bitmaps) are not full hardware offload at line rate. Proposed direction (name for indexing): reformulate tracking around EC stripe semantics + per-path progress so required state scales with Bandwidth-Jitter Product (inter-path RTT difference) rather than end-to-end BDP; then a cache of loss records instead of a full arrival bitmap. Eq. 1 on p.3 maps PSN → stripe offset and path id (PSN mod n). Full cache pipeline unread past p.3.

### 负载

Scale-across LLM training: tens–hundreds of thousands of GPUs across sites (GPT-4 ~25k A100; GPT-5-scale ~200k; Colossus roadmap toward 1M). Inter-DC fabric is high-latency, high-BDP, lossy; PFC pause buffering becomes impractical at millisecond RTT. Retransmission-based RDMA recovery amplifies FCT by tens-of-ms RTTs. Multi-path / packet spraying improves utilization but delivers out-of-order arrivals that the NIC must track for message completion and for erasure-coded reconstruction (need to know which packets are missing). Workload implication: many concurrent RDMA connections carrying large messages at multi-hundred-Gbps to Tbps line rates, with reordering across paths and occasional loss—receiver state and datapath logic must keep up without host round-trips.

### 仿真方法学

Abstract claims (line-rate ≥400 Gbps; 6× more concurrent connections vs SOTA SoC; scalability toward 1.6 Tbps) are unpaid until unread eval. Paid characterization on p.1–3: Fig. 2 bitmap size vs RTT at 400 Gbps and 1.6 Tbps (linear growth; 4×/5× callouts); Alveo U280 ~9 MiB BRAM with DMA/CMAC consuming a share. No full test harness, traffic trace, or FPGA utilization table on these pages. Treat abstract throughput/connection multipliers as unpaid.

### 工业可行性

Product move is FPGA SmartNIC receive offload for EC-RDMA WAN—aligned with production FPGA RDMA deployments already named (Microsoft lineage). Constraints already on p.1–3: on-chip BRAM budget (~9 MiB class) vs BDP-proportional bitmaps; need to coexist with DMA/CMAC IP; multi-path + EC changes completion semantics vs classic RoCE; header/PSN mapping assumptions (source port as path proxy, round-robin PSN→port). Abstract 400 Gbps / 6× unpaid; ASIC NIC port of the same cache tracker not discussed on these pages.

## Master Class

1. **The Real Abstract** — Scale-across AI fabrics force RDMA onto lossy, multi-path, millisecond-RTT WANs. Erasure coding avoids RTT-amplified retransmit, but only if the NIC can track arrivals/losses at line rate—and classic BDP-sized bitmaps do not fit FPGA BRAM.

2. **The Rashomon Synthesis** — Transport people add EC and multipath; datacenter RDMA people keep PFC+bitmap receivers; FPGA NIC people offload RoCE datapaths sized for intra-DC BDP. The leftover problem is receiver state that must cover WAN BDP × multipath reordering inside a few MiB of BRAM at ≥400 Gbps.

3. **The Magic Trick** — Track EC stripes / lost packets in a compact on-NIC cache so state follows inter-path jitter, not end-to-end BDP.

4. **The Skeleton in the Closet** — 400 Gbps / 6× / 1.6 Tbps are abstract-only on p.1–3; Fig. 2 is a sizing argument not a measured design point; full cache pipeline and multi-connection stress unread; path-id-via-source-port assumption may not match all WAN load balancers.

5. **可提取的问题线索**（仅 p.1–3，有数字，无机制名）

1. 超大规模训练已到数万～数十万 GPU：GPT-4 约用 25,000 块 A100；后续规模报道约 15× 至约 20 万 GPU，并有通向约 100 万 GPU 的路线图——单数据中心供电/散热不够，必须跨站点互联。(p.1)
2. 跨广域网时，基于重传的丢包恢复会把往返时延放大到数十毫秒量级，严重拉长流完成时间。(p.1)
3. 传统按 inflight 位图跟踪乱序到达时，位图容量需覆盖全部在途包，大小随带宽–时延积（因而在固定带宽下随 RTT）近似线性增长；在 400 Gbps 与 1.6 Tbps 量级下，随 RTT（约 5–25 ms）升至数十～上百 KiB/连接量级（文中示意约 4×/5× 跃迁）。(p.3, Fig.2)
4. 典型 FPGA NIC 片上 BRAM 约 9 MiB（Alveo U280），且一部分已留给 DMA/CMAC 等 IP；在 WAN RTT 与 Tbps 级速率下，按 BDP 计的位图会迅速超出片上存储并成为数据通路瓶颈。(p.3)
5. 多路径喷洒在提升利用率的同时，使接收端面对跨路径乱序与抖动；纠删恢复又要求精确知道哪些包缺失——接收状态与完成逻辑必须在线速下同时支撑高带宽、多连接与乱序。(p.1–2)
